# Project maintenance notes

## 2026-10-24 — Fixed widget appearance and independent system entry points

- Applies to the compact widget and expanded page on macOS and Windows.
- Symptom: Windows in dark mode could still show a light widget when its separate app mode was light. The native window followed `AppsUseLightTheme`, while the shared browser page already used a fixed dark palette.
- Keep widget surfaces on the accepted macOS dark-gray palette (`#20252D`). On Windows, legacy `-Theme System/Light/Dark` inputs remain accepted for compatibility and all select the fixed appearance. Dynamic inline controls must receive the same palette without rebuilding the visible tree on repeated checks.
- On macOS, pin only the content root to Dark Aqua. Do not set the entire application's appearance: native menus and menu-bar numerals should retain system behavior.
- Windows tray numeral contrast follows `SystemUsesLightTheme` independently. Preserve this lookup when changing window styling; taskbar and app modes can differ.
- Verification: `windows/test/native-appearance.tests.ps1` executes palette selection with fabricated modes; `windows/test/native-ui-parity.tests.ps1` checks actual WinForms surfaces and tray pixels on Windows. `macos/test/native-appearance.test.mjs` executes production content setup and compact drawing under Aqua/Dark Aqua. Follow CONTRIBUTING for full core and native suites.
- These automated checks do not establish physical Windows/macOS theme-switch acceptance or absence of transient white flashes. Verify those on the target desktop before reporting them as passed; keep private evidence outside this repository.

## 2026-10-24 — AppKit bitmap tests on wide-gamut displays

- Applies when comparing rendered AppKit pixels with literal sRGB palette values.
- Symptom: a Display P3 compact-view bitmap sampled through `colorAt(...).usingColorSpace(.sRGB)` returned `[44,49,58]` for the intended dark background; the unconverted bitmap carried `[33,37,44]` and a Display P3 profile.
- Convert the bitmap with `converting(to: .sRGB, renderingIntent: .default)` before `getPixel`. The same saved bitmap then returned the exact sRGB `[32,37,45,255]`. Sample clear canvas outside the ring's antialiased edge.
- This corrects the test's color-space handling, without changing the shipped palette. The native appearance regression uses the profile-aware path and keeps the literal background assertion.

## 2026-10-24 — Bound local application copies after an authorized update

- Applies to local macOS build outputs, extracted CI packages, and rollback application bundles.
- Symptom: macOS storage listed many identical-version applications. Completed updates had accumulated full `.app` backups and extracted/build copies; each included its own Node runtime. The executable copies were independent of the active installation and user-data directory.
- The user approved retaining the active installation and the latest pre-update rollback, and deleting the other 23 identified bundles. Cleanup used an explicit path allowlist, validated bundle identities and protected paths, and checked that no candidate was running. Only the `.app` directories were removed; their parent evidence folders and data backups were retained.
- Verification: a fresh bundle scan found exactly the two retained applications. Both application manifests, settings and native preferences were unchanged; existing recovery/public records were preserved, the same processes remained running, and the service health check passed. The detailed private deletion receipt remains outside Git.
- Implemented workflow: use `scripts/update-macos.mjs prepare --config …`, open the installed app normally, then `verify --receipt …` as documented in CONTRIBUTING. Preparation validates the exact successful CI package and saves data/preferences before replacing the app in place. Verification checks payload, runtime ownership, local service, settings and history, then automatically prunes registered packages, extracted apps and older rollbacks. The first managed update can adopt the explicitly identified legacy rollback; retain it until the new app passes verification. A failed/interrupted check never authorizes cleanup, and an unsafe/running/modified candidate blocks pruning with a retryable receipt.
- Keep cache artifacts separate from evidence. Cleanup removes only registered artifact leaves; it never removes parent evidence directories, saved data snapshots, logs or screenshots. It does not discover arbitrary unregistered builds. Experimental builds should use temporary output and remove that output after checking it. The maintained workflow replaces the per-release private installers that caused accumulation.
- Identify retained packages and receipts by commit and CI run, rather than relying on the unchanged product version alone. Include the remaining application-copy count and cleanup result in the delivery checklist.
- Verification for the maintained workflow: isolated transaction tests use actual temporary copies/renames/removals across successive updates and failures, including first-use migration, payload/history preservation, symlink/overlap, process and retry guards. A real in-place update remains a separate acceptance step; these fixtures do not prove it has run. This workflow does not install a scheduled or background cleanup job.
- Independent review identified state-directory binding, PR-merge provenance, modified extracted copies and swallowed preference-read failures; each now has a failing-before/fixed-after regression. Resolve path casing before overlap checks on case-insensitive volumes. Final local checks: 40 updater-specific tests, 57 tooling tests in total, both 258-test core suites, docs and shared-file checks passed. A read-only native probe verified the installed app and an isolated eligible CI package; it did not stop or replace the formal installation. Keep that distinction when adopting this workflow.

Preparation now checks the process inventory independently after Stop and before any data snapshot or swap.
